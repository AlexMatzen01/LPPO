    v5.3.0 Systems Language

    LPPO — Legible Programming Platform eXtensions

    A statically typed systems language with zero-cost abstractions, explicit memory/ownership, first-class concurrency, and a portable bytecode interpreter. Compile to C, bundle a standalone executable, or target bare-metal x86_64.

    Getting Started

    1Toolchain & Installation

    LPPO is a single binary with an embedded interpreter. On first run it installs itself to ~/.LPPO/bin/lppo and adds that directory to your shell PATH.

    Build from source

    Build

    cargo build --release
./target/release/lppo --version

    Requires Rust 2021 edition. Workspace members: lppo, lppo-rt, version-cli.

    Quick start

    Run a file

    echo 'pub proc main() -> Void { out "Hello, LPPO!"; }' > hello.lppo
lppo hello.lppo
    Native build

    Compile to C / executable

    lppo build hello.lppo -o hello
./hello

    Transpiles to C via the codegen backend and invokes the system compiler.

    Bundle

    Self-contained executable

    lppo compile hello bin/hello
lppo compile-bare-metal kernel bin/kernel

    compile embeds bytecode in a copy of the interpreter; compile-bare-metal targets x86_64-none.

    Project scaffolding

    lppo project init myapp --path ./myapp
cd myapp
lppo project run

    This creates lppo.toml, src/main.lppo, .gitignore, .lppo/ (with repositories.json), and initializes a git repository.

    Language Reference

    2Core Language

    LPPO is statically typed with explicit annotations on every binding and parameter. Types are erased at runtime (compile-time only); the runtime operates on tagged values.

    2.1 Lexical grammar

    Comments: // line and /* block */. Identifiers are alphanumeric plus _. Literals include integers, floats, strings ("..."), chars ('x'), bytes (b'A'), and raw strings.

    CategoryExamples
    Keywordsproc out input let if elif else while for in loop break continue return struct enum trait impl match new module use pub ring alloc dealloc ref deref move copy borrow mut own scope end unsafe async await spawn parallel call
    TypesInt64 Bool Str Arr<T> Void Option<T> Result<T,E> Map<K,V> Set<T> Float32|Float64 Char Byte Fn(...) -> R
    Operators+ - * / % ^ == != < <= > >= and or not & | ^ ~ << >> += -= *= /= .. (range) => (fat arrow)
    Literals42 3.14 "hi" true false 'A' b'0' [1,2,3]

    2.2 Bindings, mutability & ownership

    Immutable by default

    let

    let x: Int64 = 42;      // immutable
let mut y: Int64 = 1;   // mutable
let z: Ref = borrow s;
    Ownership kinds

    Own / Ref / MutRef / Borrow

    let a: Own = move x;
let b: Ref = ref x;
let c: MutRef = borrow mut x;
    Memory

    alloc / dealloc

    alloc buf: Arr on heap size 1024;
dealloc buf;

    Heap allocations are auto-deallocated at scope exit; stack allocations are not tracked.

    2.3 Type system

    KindForms
    PrimitivesInt64 Bool Str Char Byte Void Float32 Float64
    ContainersArr<T> Option<T> Result<T,E> Map<K,V> Set<T> Tuple
    User-definedstruct, enum, trait, generics, type aliases, lifetimes 'a
    FunctionsFn(Params) -> Ret, closures \|p\| -> R { body }

    Structs and enums support methods and impl blocks (inherent and trait). Traits define method signatures; impl Trait for Type provides implementations. Pattern matching via match with guards.

    2.4 Control flow

    if cond { } elif cond { } else { }
while cond { }
for item in iter { }
loop { break; continue; }
match expr {
  pattern if guard => out expr;
  _ => out "default";
}

    parallel { ... } evaluates several emit expressions concurrently. scope { ... } introduces an explicit scope with automatic heap deallocation on exit.

    2.5 Functions & modules

    pub proc add(a: Int64, b: Int64) -> Int64 {
    return a + b;
}
module math {
    pub proc pi() -> Float64 { ... }
}
use math::{pi};

    Procedures require an explicit return type (-> Void if none). Header-only declarations (empty body) are merged with implementations. Imports resolve via .lppo/.lpph/.lph or index files, falling back to installed packages.

    2.6 Memory / lifetime semantics

    No garbage collector. Heap blocks are tracked by address and deallocated explicitly via dealloc or automatically at scope exit. Lifetimes 'a annotate references; ring 0; enables privileged builtins (outb, port I/O) for kernel/bare-metal code. unsafe blocks bypass borrow checking at compile time.

    2.7 Concurrency

    spawn { out "fire-and-forget"; }
let f: Future = async { 2 + 2; };
let r: Int64 = await f;
parallel { out "a"; out "b"; }

    spawn runs a block in a new thread returning a JoinHandle. async returns a Future resolved with await. parallel emits branches concurrently.

    Idioms & Performance

    4Idioms & Anti-Patterns

    Idiomatic

    Prefer immutable bindings

    let x: Int64 = compute();  // good
let mut x: Int64 = compute(); // only if mutated
    Anti-pattern

    Avoid unnecessary mut

    let mut x: Int64 = 5;   // never reassigned
out x;
    Idiomatic

    Scope heap allocs

    scope {
    alloc buf: Arr on heap size 4096;
    // buf auto-deallocated here
}
    Anti-pattern

    Leaking heap memory

    alloc buf on heap size 4096;
// no dealloc — freed only at process exit
    Idiomatic

    Use match over nested if

    match v {
  Some(x) => out x;
  None => out "absent";
}
    Anti-pattern

    Blocking in async

    async { await heavy(); }  // good
async { pause heavy(); }   // blocks the async task

    Memory model

    LPPO uses manual memory management with deterministic deallocation. Every alloc ... on heap is paired with a dealloc, either explicitly or automatically when the scope exits. Values are tagged at runtime (int/float/bool/str/array/tuple/map/set/struct/enum/fn) so the runtime can render, compare, and serialize them uniformly. There is no garbage collector; long-running programs should dealloc or use lppo_rt_cleanup at process boundaries.

    Compilation pipeline

    Source → Lexer → Parser → AST → Type Checker → Compiler (bytecode ops) → (interpreter | C transpiler | bare-metal embed). The bytecode is JSON-serializable and can be stripped, obfuscated (XOR), and dead-code eliminated from main.

    FAQ

    5Frequently Asked Questions

    What is LPPO?

    LPPO (Legible Programming Platform eXtensions) is a statically typed systems language with explicit memory/ownership, first-class concurrency, and a portable bytecode interpreter, C transpiler, and bare-metal target.

    What file extensions does LPPO use?

    .lppo (implementation), .lpph and .lph (header/declaration). Entry point is pub proc main() -> Void.

    Is there a garbage collector?

    No. Memory is managed explicitly with alloc/dealloc and automatic scope-exit deallocation for heap allocations.

    Can it run on bare metal?

    Yes. lppo compile-bare-metal produces an x86_64-unknown-none kernel using lppo-bare-rt with VGA, serial, keyboard, paging, GDT/IDT, and port I/O.

    How do packages work?

    lppo pkg install|search|list|info|remove|build|update manages packages from git/path repositories. Native packages expose LPPO-facing FFI functions and are installed to ~/.LPPO/ or project-local .lppo/. See packages.md.

    What is ring 0?

    ring 0; declares privileged kernel code enabling builtins like outb/inb for port I/O. Required for bare-metal and systems programming.
